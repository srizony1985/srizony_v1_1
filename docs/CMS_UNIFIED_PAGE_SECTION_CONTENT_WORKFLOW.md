# Srizony CMS: unified page, section and site-content workflow

## Core model

The CMS now separates **where content lives**, **what records exist**, and **how a section displays them**:

- **Navigation / Pages** define destinations and route hierarchy.
- **Page Builder** defines page sections and each section's linked content collection and presentation rules.
- **Site Content** manages the shared content records. A record created from a section editor is the same database record shown in the Site Content library; there is no second copy stored in the page JSON.
- **Page, section, menu and content visibility** are independent publishing controls.

The authoritative content store is Neon PostgreSQL. `data/` is not a public runtime content source; bundled datasets are confined to the fallback gateway and seed/bootstrap paths.

## 1. Navigation creates pages

Open **Admin Dashboard → Site Navigation**.

- Creating a top-level menu with a slug creates a matching CMS page at `/{menu-slug}`.
- Creating a submenu under a top-level menu creates a page at `/{menu-slug}/{submenu-slug}`.
- Reordering, renaming, moving or hiding a navigation item is managed in Site Navigation.
- The destination page's publication status is managed separately in Page Builder.

Page routes are generated by the navigation service, not manually duplicated in a second page form. Slugs are normalized and route collisions are checked before saving.

## 2. Page Builder defines a section collection

Open **Admin Dashboard → Page Builder**, select a page, and add a section.

The section type determines the public visual renderer. Its `contentCollection` definition determines the linked collection and presentation configuration:

```ts
contentCollection: {
  enabled: true,
  component: 'project',
  maxItems: 12,
  layout: 'grid',
  columns: 3,
  gap: 24,
  viewportItems: 3
}
```

The controls mean:

- **Content type**: which Site Content records belong to this collection (Projects, News, Success Stories, Statistics, Reports, etc.).
- **Maximum records**: how many published records the section can render.
- **Arrangement**: a section-compatible layout such as grid, carousel, masonry or list.
- **Desktop columns**: the number of desktop grid / masonry columns.
- **Gap**: spacing between collection items, in pixels.
- **Cards visible in viewport**: available for carousel/scroller layouts only.

The CMS restricts the layout choices to the arrangements supported by that section type. CTA and donation sections are single-record presentations and are capped at one record.

New Statistics sections default to the **Statistics** Site Content type. Statistics are stored as individual CMS records, with a display value, bilingual title/label, note, and optional icon, reusable illustration or custom image. Values such as `125+`, `92%` and `1.2M` are preserved as display strings.

### Section types and collection presentation

| Page section type | Default Site Content type | Supported presentation |
|---|---|---|
| Cards | Projects | Grid, carousel, masonry, list |
| Gallery | Projects / image-backed records | Grid, masonry |
| Carousel | News | Carousel, grid, list |
| Stats | Statistics | Grid, list |
| Rich text | Projects / narrative records | List |
| Timeline | Projects / dated records | List |
| Notice list | Notices | List |
| Reports | Reports | List |
| Table | Records for tabular display | List |
| CTA / Donation | Selected content record | Single record |
| Content feed | Selected content type | Grid, carousel, masonry, list |

The content type is selectable, so a section can display another suitable collection without changing the content records themselves.

## 3. Site Content is a shared library

Open **Admin Dashboard → Site Content**.

Records may be created in either place:

- **From Page Builder**: the manager preselects the section's content type and destination page. The content editor saves the record to the shared `cms_content_items` table.
- **From Site Content**: select a content type, create the record, and select its “Publish under page” destination. If the destination does not yet have a matching collection section, the content service creates or joins one automatically.

The same record appears in both editors because both query the same component and route-parent combination. Updating a record in either place updates the same database row.

News and Success Stories are special canonical content types:

- News collection and detail pages: `/news` and `/news/{news-slug}`. The old `/what-we-do/news` page record is removed.
- Success Stories collection and detail pages: `/success-stories` and `/success-stories/{story-slug}`. The old `/what-we-do/success-stories` page record is removed.

Statistics use the default collection page `/impact/statistics`, but a Statistics record can also be assigned to a page section by creating it from that section's manager.

## 4. Visibility controls

| What is being shown? | Where visibility is managed | Effect |
|---|---|---|
| Menu item | Site Navigation | Shows/hides the link in navigation |
| Page | Page Builder → Publication status | Published pages can be served; drafts and archived pages are not public |
| Section | Page Builder → Section visibility | Hides/shows that section without deleting it |
| Content record | Site Content / inline Content Editor | Published records are eligible for feeds; draft/hidden records are not |

Hiding or deleting a section does not delete the underlying Site Content records. Hiding a menu item does not by itself unpublish its page. These states are intentionally independent.

## 5. Theme and colour selection

The theme/colour chooser has been removed from the CMS administration workflow. The public site uses the fixed Srizony design system and its semantic theme tokens. The old theme API returns HTTP 410, and legacy theme overrides in old database documents are ignored by the public renderer.

## 6. Export and mass-edit import

Open **Admin Dashboard → Settings → CMS site-data transfer**.

1. Click **Export CMS data (.json)** to download an importable database snapshot.
2. Keep the exported structure and table/column names intact while editing values.
3. Keep primary keys for existing records so imports can update the intended rows.
4. To add independent records in tables with a generated single-column ID, a new row may omit that generated ID. Rows with foreign-key dependencies need valid referenced IDs.
5. Select the modified JSON and inspect the table/record count preview.
6. Confirm **Apply JSON changes** to upsert the supplied records.

### File format

The JSON file has this envelope:

```json
{
  "format": "srizony-cms-site-data",
  "version": 1,
  "exportedAt": "2026-10-31T00:00:00.000Z",
  "mode": "merge-upsert",
  "includedTables": ["pages", "cms_content_items"],
  "data": {
    "pages": [],
    "cms_content_items": []
  }
}
```

The real export includes the available whitelisted CMS tables, not only the two illustrative arrays above. JSON/JSONB columns remain structured JSON; PostgreSQL `bigint` values are serialized as strings to avoid JavaScript precision loss.

### Import behaviour and safety

- The importer is admin-only and enforces a 20 MB file limit and 50,000 rows per table.
- It rejects unknown tables, unknown columns, malformed row arrays, duplicate primary keys and records without required primary keys before writing.
- Existing rows are updated by primary key; supported new identity/serial rows receive database-generated IDs.
- Rows omitted from the JSON are **not deleted**.
- Export includes editable site/CMS records and media metadata/URLs, not the uploaded binary files. Media binaries remain in the configured media storage.
- Authentication, CMS users/password hashes, audit/login data, visitor analytics, application submissions, job applications, donations/transactions and other private operational tables are intentionally excluded from the mass-edit export.
- The importer preflights table/column/key compatibility before writes, but applies table batches sequentially rather than as one all-or-nothing transaction. Export a fresh backup first and test a large import against a staging database/branch before production.
- Preserve database IDs when editing parent/child tables. Newly generated IDs cannot automatically repair foreign keys in other rows that refer to an ID you omitted or changed.

## 7. Developer implementation notes

- Page documents continue to store section identity and `contentCollection` presentation metadata in `pages.render_cache`.
- Collection records are stored in `cms_content_items`; component-specific values such as metric `value`, `icon`, `illustration`, and `displayOrder` are in the JSONB `attributes` column.
- `lib/cms/content.ts` is the shared content repository for validation, route ownership, collection attachment and published feeds.
- `lib/site.ts` hydrates collection records into the page section's visual data shape.
- `app/admin/dashboard/page-builder/page.tsx` owns section presentation controls and inline content editing.
- `app/admin/dashboard/site-content/page.tsx` is the library view over the same records.
- `lib/cms/dataTransfer.ts` is the explicit allowlist for portable public CMS tables. Do not add auth, private submission or transaction tables to it without an explicit security and privacy review.
- Theme selection has intentionally not been brought into the export allowlist as a separate editable feature.

## Deployment checklist

After replacing the project files:

```bash
npm ci
npm run db:bootstrap
npm run test:functional
npx tsc --noEmit
npm run build
```

`db:bootstrap` runs normal migrations and the structural seed; it is not the destructive `db:seed:reset` operation. Keep the existing production `.env`/`.env.local` configuration and run the first import/large mass update against a staging Neon branch.
